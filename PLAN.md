## Часть G. Импорт PDF-выписок: точный разбор Kaspi и Freedom (план от 2026-07-08)

Цель: пользователь выбирает PDF-выписку → приложение извлекает **только строки операций** (дата, сумма, доход/расход, описание), присваивает категории и показывает предпросмотр. Данные клиента (ФИО, номер счёта, IBAN) из шапки **не извлекаются и не сохраняются** — парсер берёт только строки, начинающиеся с даты и содержащие сумму со знаком; всё остальное игнорируется. Образцы — в `bank_statement/` (kaspi.pdf, freedom-.pdf).

Наблюдения по форматам (из образцов):

| | Kaspi | Freedom |
|---|---|---|
| Строка | `30.06.26 + 470,00 ₸ Пополнение Сұлтан С.` | `28.06.2026 -4,000.00 ₸ KZT Покупка MAGNUM...` |
| Дата | `dd.MM.yy` | `dd.MM.yyyy` |
| Сумма | `1 234,56` (пробел — тысячи, запятая — дробь) | `1,234.00` (запятая — тысячи, точка — дробь!) |
| Тип | знак `+`/`-` перед суммой | знак в самой сумме |
| Операция | Пополнение / Снятие / Перевод / Покупка / Разное / «Перевод на свой счет» | Покупка / Перевод / Платеж / Пополнение / «Сумма в обработке» |
| Особенности | перенос длинных операций на 2 строки | многострочные детали (Payment for ОНАЙ…), колонка валюты, встречается USD |

Этапы (каждый — тест сначала, всё в `shared/commonMain`, чистый Kotlin):

- [x] **G3. `KaspiStatementParser`** — якорь `dd.MM.yy`, склейка переносов.
- [x] **G4. `FreedomStatementParser`** — якорь `dd.MM.yyyy`, пропуск не-KZT.
- [ ] **G5. Категоризация (порядок приоритета):**
  1. merchant rules пользователя (уже есть);
  2. словарь мерчантов КЗ: MAGNUM/SUPERMARKET → Продукты; KFC/SELI POYELI/STARBUCKS/UMMA FOOD/BAURSAK → Кофе и Рестораны; WHOOSH/ОНАЙ/ONAY → Транспорт; Beeline/Tele2/Altel → Связь/Подписки; «Зарплата» → Зарплата;

## Часть K. Скользящие периоды «Неделя» и «Месяц» (план от 2026-07-14)

Проблема: после импорта PDF кнопка «Неделя» показывает 1–2 операции. ## Часть L. Динамическое свечение по датчикам (план от 2026-07-15)

Идея: карточки, чипы и FAB получают мягкое свечение (glow), которое «перетекает» по контуру элемента при наклоне телефона — как блик на стекле. Источник данных — датчики положения устройства.

Ключевые решения:

- **Датчик — `TYPE_GAME_ROTATION_VECTOR`** (fusion гироскопа и акселерометра, без магнитометра): даёт стабильный наклон без дрейфа чистого гироскопа и без дрожания сырого акселерометра. Fallback-цепочка: `GAME_ROTATION_VECTOR` → `ROTATION_VECTOR` → `ACCELEROMETER` → датчиков нет → свечение статичное (сверху по центру), приложение работает как раньше.
- **Одна подписка на приложение**, не по одной на элемент: `TiltSensorMonitor` в `app/` слушает датчик и публикует `StateFlow<TiltOffset>`; вниз по дереву — через `CompositionLocal`. Частота `SENSOR_DELAY_GAME`, подписка живёт только в `RESUMED` (lifecycle-aware) — фон не жрёт батарею.
- **Математика — чистый Kotlin в `shared/commonMain`** (правило 7): преобразование кватерниона/векторов в нормализованный `TiltOffset(x, y ∈ -1..1)`, низкочастотный фильтр сглаживания, ограничение углов. Android-обёртка в `app/` только конвертирует `SensorEvent` в числа.
- **Отрисовка — один `Modifier.tiltGlow(...)`**: `drawBehind` с радиальным градиентом (цвет `MaterialTheme.colorScheme.primary`, альфа ~0.25–0.4), центр блика смещается по `TiltOffset`; поверх смещения — `animateOffsetAsState`/spring для плавности. Никаких `RenderEffect`/blur (API 31+) в первой версии — обычный градиент работает с minSdk и дешевле по GPU.
- **Уважение к пользователю**: тумблер «Динамические эффекты» в Профиле (`Settings` + DataStore, по умолчанию вкл.); при выключенном тумблере или `Settings.Global.ANIMATOR_DURATION_SCALE == 0` (анимации отключены в системе) — датчик не слушаем вовсе.

Этапы (тест сначала для shared-логики):

- [x] **L1. Тесты и модель наклона**
- [x] **L2. `TiltSensorMonitor`**
- [x] **L3. `LocalTiltOffset` + `Modifier.tiltGlow`**
- [x] **L4. Применение к элементам**

## Часть N. Подкатегории (план от 2026-07-15)

Цель: у категории может быть родитель — один уровень вложенности («Продукты» → «Magnum», «Мясо»; «Транспорт» → «Такси», «Whoosh»). Глубже одного уровня **не делаем** — сложность растёт квадратично, а пользы для личного учёта нет.

Ключевые решения:

- **Схема**: `parentId: Long?` в `CategoryEntity` (+ индекс), `NULL` = корневая. Миграция Room `MIGRATION_3_4` (правило 5: только через `DatabaseMigrations.kt`, bump до версии 4). `ON DELETE`: при удалении родителя подкатегории становятся корневыми (`SET NULL` семантика через код репозитория, чтобы не терять транзакции).
- **Инварианты в `shared/commonMain`** (тесты сначала): подкатегория не может иметь детей (глубина ≤ 1); `parentId` только на категорию того же `type` (расход к расходу); запрет циклов; системные категории («Переводы») без детей. Валидатор `CategoryHierarchyValidator` — чистый Kotlin.
- **Агрегация**: в Аналитике донат и рейтинг считаются по **корневым** категориям (суммы подкатегорий сворачиваются в родителя); тап по строке родителя раскрывает разбивку по подкатегориям. Rollup-логика — `shared/commonMain` (`CategoryRollup`), с тестами.
- **Ввод**: в `TransactionDialog` выбор категории — двухшаговый только при наличии детей (выбрал «Продукты» → чипы подкатегорий + «Без уточнения»). Транзакция ссылается на конкретную категорию (родителя или подкатегорию) — модель `TransactionEntity` не меняется.
- **Классификатор и merchant rules** работают как раньше — категория есть категория; словарь мерчантов (G5) сможет целиться в подкатегории.

## Готовность к iOS (Android + iOS из одной кодовой базы)

Целевая структура — стандартная KMP-компоновка:

```
walletai/
├── shared/      commonMain (логика) + androidMain + iosMain   ← уже есть
├── app/         Android-приложение                             ← уже есть
└── iosApp/      Xcode-проект, подключает shared framework      ← появится в конце
```

Что уже переносимо (лежит в `shared/commonMain`, Android-классов нет): domain-модели (`Money`, `Currency`, `Period`, `TransactionType`), ML (классификатор, парсер выписки, голосовой парсер), `MoneyFormatter`, `PeriodFilter` + их тесты.

Что пока держит логику в `app/` и порядок съезда:

| Компонент | Сейчас | KMP-замена | Когда |
|---|---|---|---|
| Сеть (Gemini) | ✅ Ktor + kotlinx.serialization в `shared/ai` (OkHttp-движок на Android, Darwin на iOS) | — | готово (C4) |
| БД | Room (androidx) | Room KMP 2.7+ (та же аннотационная модель) | после C4 |
| Настройки | DataStore (androidx) | DataStore KMP (официально мультиплатформенный) | вместе с БД |
| DI | Koin | Koin (уже KMP) | готово |
| UI | Jetpack Compose | Compose Multiplatform (те же экраны) | последним |
| Голос, экспорт, уведомления, FileProvider | Android API | остаются платформенными: `expect/actual` или отдельные реализации в iosApp | по факту |

Правило до тех пор: новая бизнес-логика — только в `shared/commonMain`; в `app/` — только UI и платформенные обёртки.
