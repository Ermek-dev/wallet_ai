## 2. Безопасность — оценка и проблемы

### 2.1 Критично
- **Gemini API-ключ зашивается в APK** (`BuildConfig.GEMINI_API_KEY`). Любой ключ, попавший в клиентское приложение, извлекается декомпиляцией за минуты. Для pet-проекта на своём телефоне — терпимо; для публикации в Google Play — недопустимо.
  **Решение (по мере роста):**
  1. Сейчас: оставить как есть, но поставить лимиты на ключ в Google Cloud Console (quota + restriction по package name / SHA-1).
  2. Позже: перейти на **Firebase AI Logic** (зависимость `firebase-ai` уже подключена, но не используется!) — ключ не хранится в приложении, есть App Check.
  3. Идеал: свой лёгкий backend-прокси.
- **Ключ передаётся в URL как query-параметр** (`?key=$apiKey`) — URL попадают в логи прокси/серверов. Перенести в заголовок `x-goog-api-key`.

### 2.2 Средне
- `android:allowBackup="true"` — финансовая БД попадает в облачный бэкап Google в открытом виде. Либо отключить, либо настроить `backup_rules.xml` (исключить БД), либо оставить осознанно (удобно при смене телефона).
- Тело ошибки API пишется в `Log.e` — в release-сборке логи стоит отключить (Timber + release tree, или ProGuard-правило для стриппинга Log).
- `logging-interceptor` подключён в зависимостях — если когда-нибудь включится, будет логировать тела запросов (включая финансовые данные). Убрать или ограничить debug-сборкой.
- Room БД не шифруется. Для локального личного приложения это норм (Android sandbox защищает), но как опция роста — SQLCipher.

### 2.3 Нормально сделано
- HTTPS, таймауты у OkHttp, экранирование JSON через `JSONObject.quote`, release-подпись через переменные окружения (пароли не в коде), `.env` в `.gitignore`.

## 3. Архитектура и качество кода

### 3.1 Clean Architecture — сейчас её нет
Текущая структура — «ViewModel-комбайн»: `FinanceViewModel` напрямую держит DAO, `GeminiService`, `Exporter`, классификатор и всю бизнес-логику (парсинг выписки, фильтрация, обучение модели). Слоёв нет, интерфейсов нет, DI нет.

Целевая структура (эволюционно, не всё сразу):

```
ui/            – Compose-экраны + ViewModels (по одному на экран)
domain/        – модели (Transaction, Category, Money), use-cases, интерфейсы репозиториев
data/          – Room, репозитории-реализации, GeminiService, DataStore настроек
```

Ключевые шаги:
- **Repository-слой**: `TransactionRepository`, `CategoryRepository`, `AdviceRepository`, `SettingsRepository` — ViewModel не должен знать про Room и OkHttp.
- **DI — Koin** (проще Hilt для новичка и, главное, работает в KMP — задел на iOS).
- **Разбить FinanceViewModel** на `DashboardViewModel`, `AnalyticsViewModel`, `AdvisorViewModel`.
- **Enum вместо строк**: `enum class TransactionType { INCOME, EXPENSE }`, `enum class Period { WEEK, MONTH, THREE_MONTHS, ALL }` — сейчас магические строки `"INCOME"`, `"MONTH"` размазаны по всему коду.

### 3.2 Проблемы данных
- **Деньги хранятся как `Double`** — классическая ошибка: накопление ошибок округления (0.1 + 0.2 ≠ 0.3). Правильно: `Long` в минорных единицах (тиын/копейки) + класс `Money(amount: Long, currency: Currency)`. Это же понадобится для мультивалютности.
- **Нет ForeignKey и индексов** в Room: `TransactionEntity.categoryId` не связан с `categories` — можно удалить категорию, и транзакции «осиротеют». Добавить `@ForeignKey` + `Index(categoryId)`, стратегию `onDelete`.
- `fallbackToDestructiveMigration()` — при изменении схемы **все данные пользователя стираются**. Заменить на нормальные `Migration` + `exportSchema = true` (файлы схем в git).
- `OnConflictStrategy.REPLACE` на insert транзакций — при коллизии id молча перезапишет запись; для авто-id это скрытая мина.

### 3.3 Проблемы UI-слоя
- `viewModel.getFilteredTransactions(transactions)` вызывается прямо в composition → пересчёт на каждой рекомпозиции. Правильно: сделать `filteredTransactions` = `combine(transactions, selectedPeriod)` StateFlow во ViewModel.
- `selectedTab by remember` в MainActivity — при повороте экрана/смерти процесса таб сбрасывается. Минимум `rememberSaveable`, лучше — Navigation Compose (пригодится при росте числа экранов).
- Все строки («Текущий Баланс», «Внести»…) захардкожены в Kotlin, а не в `strings.xml` → локализация (ru/kk/en) невозможна. Постепенно переносить в ресурсы.
- `collectAsState()` → лучше `collectAsStateWithLifecycle()` (зависимость уже есть).
- Дублируется свой composable `FlowRow`-обёртка — можно убрать.
- Форматирование денег через `String.format("%.2f")` без единого форматтера — сделать одну функцию `Money.format()` с учётом локали и валюты.

### 3.4 ML-классификатор
- В `classify()` для незнакомых слов используется `likelihoods.size` как «число слов категории» — это размер словаря, а не счётчик слов категории. Модель работает, но сглаживание математически неверное → хранить реальный `totalCatWords` в `TrainedModel`.
- Fallback-словарь ключевых слов (Пятёрочка, МосОблЕИРЦ…) заточен под Россию — для Казахстана добавить Magnum, Small, Kaspi, Halyk, Wolt, Glovo, Onay и т.д.
- Переобучение модели на каждом insert — при тысячах транзакций станет заметно; позже — debounce или обучение по требованию.

### 3.5 Зависимости — мусор
Не используются, но подключены: `retrofit`, `converter-moshi`, `moshi` (+codegen через KSP), `firebase-ai`, `firebase-appcheck`, `google-services` plugin. Либо начать использовать (Retrofit/Moshi вместо ручного JSON в GeminiService — хорошая идея; Firebase AI — см. безопасность), либо удалить — сейчас они раздувают APK и время сборки.

### 3.6 Прочее
- `namespace`/`applicationId = "com.example"` — нельзя публиковать в Play с таким id. Сменить на свой, например `kz.abdiyev.walletai` (см. Фазу 1).
- Тесты только шаблонные (`ExampleUnitTest`). Naive Bayes, парсер выписки и фильтрация периодов — идеальные кандидаты для первых unit-тестов (чистая логика без Android).
- Проект не в git (`Is a git repository: false`) — **инициализировать git первым делом**, до любых правок.

### Фаза 7 — Голосовой ввод транзакций (3–5 дней)
Сценарий: пользователь нажимает микрофон и говорит «потратил 3400 в Сели Поели» → приложение само создаёт черновик: сумма 3400 ₸, расход, категория «Кофе и Рестораны» → пользователь одним тапом подтверждает (или поправляет категорию — и модель это запоминает).

Как это устроено технически:
- [ ] **Распознавание речи — Android `SpeechRecognizer`** (системный, on-device): бесплатно, быстро, без API-ключей, аудио не хранится. Это самый безопасный вариант — в облако ничего не уходит. Разрешение `RECORD_AUDIO` запрашивать только в момент первого нажатия на микрофон, с объяснением зачем.
- [ ] **Парсер голосовой фразы** (`VoiceInputParser`, чистый Kotlin → KMP-совместимый):
  - сумма: числа словами и цифрами («три тысячи четыреста», «3400», «3.4к»);
  - тип: «потратил/купил/заплатил» → расход, «получил/пришло/зарплата» → доход;
  - место/описание: остаток фразы («Сели Поели»).
- [ ] **Автокатегоризация** — прогонять описание через уже существующий `TransactionClassifier` (тот же пайплайн, что у парсера выписки). Ничего нового писать не надо — переиспользуем.
- [ ] **Обучение на исправлениях**: если пользователь поменял категорию в предпросмотре — сохранить пару «мерчант → категория» в отдельную таблицу `merchant_rules` (Room). При следующем «Сели Поели» правило срабатывает раньше ML-модели и даёт 100% попадание. Это важнее, чем улучшать сам ML.
- [ ] UI: кнопка-микрофон (FAB на дашборде), анимация записи, тот же экран предпросмотра, что уже есть у парсера выписки → один тап «Сохранить».
- [ ] Fallback: если распознавание недоступно (нет Google-сервисов) — обычный текстовый ввод той же фразой в то же поле.
- [ ] (Позже, опционально) сложные фразы разбирать через Gemini («вчера такси 800 и кофе 1200» → две транзакции) — но только по явному действию пользователя, и в промпт уходит только текст фразы, никаких лишних данных.

## Принципы UX/UI и system design (проверять каждую фичу)

1. **Лаконично**: 3–4 таба максимум (Учёт / Аналитика / ИИ / Профиль). Новые функции — внутрь существующих экранов, а не новые табы. Один экран = одна задача.
2. **Быстро**: главный сценарий — «внести трату» — должен занимать ≤ 5 секунд и ≤ 3 тапа (голос: 2 тапа — микрофон + подтвердить). Всё чтение — из локальной БД через Flow (мгновенно, офлайн); сеть только для ИИ-советов и она никогда не блокирует UI.
3. **Безопасно**: данные по умолчанию не покидают устройство; в Gemini уходит только агрегированная сводка, не сырая история; речь распознаётся on-device; биометрический замок опционален; каждое новое разрешение (микрофон, уведомления) запрашивается в контексте и с объяснением.
4. **Просто**: разумные значения по умолчанию (сегодняшняя дата, последняя категория, KZT), подтверждение вместо настройки, undo вместо диалогов «вы уверены?».
5. **System design**: офлайн-first (единственный источник правды — Room, UI подписан на Flow), долгие операции — в фоне с индикатором, всё новое проходит через Repository-слой (Фаза 5), бизнес-логика — чистый Kotlin без Android-классов (задел на KMP).

### Фаза 9 — Облачная синхронизация через Supabase (опционально, в конце)
**Важно понимать:** локальная БД в приложении уже есть — Room (SQLite на устройстве). Добавление доходов/расходов работает без сервера. Supabase — это НЕ замена Room, а надстройка для сценариев, которые локально невозможны:
- синхронизация между устройствами (телефон + будущий iOS);
- облачный бэкап (не потерять данные при смене телефона);
- аккаунт (Supabase Auth), если появится.

Когда браться: только после стабилизации функционала и появления реальной потребности (второе устройство). До этого — не тратить время.

- [ ] Схема Postgres зеркалит Room: `transactions`, `categories`, `merchant_rules` + `user_id`.
- [ ] **RLS (Row Level Security) обязательно** с первого дня — каждый пользователь видит только свои строки (см. `test/supabase-postgres-best-practices/references/security-rls-basics.md`).
- [ ] Архитектура: Room остаётся источником правды (офлайн-first), Supabase — фоновая синхронизация через `SyncRepository` (last-write-wins по `updated_at` для начала).
- [ ] Клиент: `supabase-kt` (KMP-совместим — работает и на iOS).
- [ ] Auth: анонимный вход или magic link; биометрия остаётся локальным замком.
- [ ] Скиллы из `test/supabase` и `test/supabase-postgres-best-practices` переместить в `.claude/skills/` на старте этой фазы.
